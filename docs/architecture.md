# Архітектура системи "Galactic Artifact Auction"

## 1. Призначення

Навчальний навантажений проєкт для лабораторної роботи з архітектури ПЗ.
Сценарій: аукціон рідкісних міжгалактичних артефактів, де в останні секунди
торгів десятки клієнтів одночасно надсилають ставки через WebSocket. Це
класичний кейс **race condition** — потрібно гарантувати, що переможе саме
та ставка, яка справді була найвищою на момент запису в базу даних, а всі
підключені клієнти побачать однаковий, консистентний стан лоту.

## 2. Компоненти системи

| Компонент | Роль |
|---|---|
| **Клієнт (браузер)** | Відкриває WebSocket-з'єднання до конкретного лоту, надсилає ставки, отримує broadcast-оновлення в реальному часі. |
| **Nginx (reverse proxy / LB)** | Термінує TLS, розподіляє WebSocket- та HTTP-з'єднання між кількома ASGI-воркерами (горизонтальне масштабування). Опційний компонент для продакшн-подібного навантаження. |
| **Django ASGI-сервер (Daphne/Uvicorn)** | Приймає HTTP та WebSocket з'єднання, виконує ASGI-застосунок Django + Channels. |
| **Django Channels layer (поверх Redis)** | Pub/sub-механізм: коли ставка прийнята, consumer публікує подію в "групу" каналу цього лоту (`lot_<id>`), а всі consumer'и, підписані на цю групу (незалежно від того, на якому ASGI-воркері вони обслуговуються), отримують подію і транслюють її своїм клієнтам. Це те, що дозволяє масштабувати WebSocket-з'єднання горизонтально на кілька процесів/машин. |
| **PostgreSQL** | Персистентне джерело правди: таблиці `Lot` (лоти), `Bid` (ставки), `User` (користувачі). Атомарність ставки гарантується транзакцією з `SELECT ... FOR UPDATE`. |
| **Redis (кеш)** | Кеш "гарячих" даних лоту — поточна найвища ставка, час завершення — для швидкого читання без звернення до PostgreSQL при кожному рендері/підключенні. Той самий Redis може використовуватись і як backend для Channels layer (окремі logical DB/namespace), і як кеш `django.core.cache`. |

## 3. Проблема race condition

У момент завершення аукціону кілька клієнтів можуть надіслати ставку майже
одночасно, наприклад:

- Клієнт A бачить поточну найвищу ставку `100` і надсилає `105`.
- Клієнт B в той самий момент теж бачить `100` (ще не отримав оновлення) і
  надсилає `103`.

Якщо обробка ставок відбувається без синхронізації, можливі два дефекти:

1. **Lost update**: обидва запити читають `current_highest_bid = 100`,
   обидва проходять перевірку `bid > current_highest_bid`, обидва
   записуються — переможцем випадково стає той, чий запис відбувся
   останнім у БД, а не той, хто дав вищу ставку.
2. **Неконсистентний broadcast**: клієнти можуть отримати події в різному
   порядку і побачити різну "поточну найвищу ставку" до того, як стан
   стабілізується.

### Способи вирішення (розглянуті / застосовані)

- **`SELECT ... FOR UPDATE` в PostgreSQL (застосовано в проєкті)** —
  consumer відкриває транзакцію, блокує рядок лоту (`Lot.objects.select_for_update()`),
  атомарно перевіряє `bid.amount > lot.current_highest_bid` і лише тоді
  оновлює лот і створює запис `Bid`. Другий конкурентний запит чекає на
  звільнення блокування рядка і бачить вже оновлене значення — тобто його
  ставка або приймається (якщо справді вища), або коректно відхиляється.
- **Атомарні Redis-операції (`WATCH`/`MULTI` або Lua-скрипт)** —
  альтернатива без походу в PostgreSQL на кожну ставку: перевірка і
  оновлення "гарячого" значення найвищої ставки виконується атомарно на
  боці Redis (Lua-скрипт гарантує атомарність read-modify-write), а запис у
  PostgreSQL відбувається асинхронно/пакетно. Підходить для дуже високого
  навантаження, коли PostgreSQL стає вузьким місцем.
- **Оптимістичне блокування через versioning** — до рядка `Lot` додається
  поле `version`; оновлення виконується умовним `UPDATE ... WHERE version = X`,
  і якщо жоден рядок не зачепило (версія вже змінилась), клієнт отримує
  помилку "ставку перебито" і має спробувати ще раз із свіжими даними.

У цьому проєкті обрано перший підхід (`SELECT ... FOR UPDATE`) як
найпростіший для навчальної демонстрації та такий, що дає сильні гарантії
консистентності "з коробки" завдяки транзакційності PostgreSQL.

## 4. Потік даних (data flow)

1. Клієнт відкриває WebSocket-з'єднання на `/ws/auction/<lot_id>/`.
2. `AuctionConsumer.connect()` додає з'єднання до групи каналу `lot_<lot_id>`
   (через channel layer на Redis).
3. Клієнт надсилає ставку (JSON: `{"amount": 105}`) через WebSocket.
4. `AuctionConsumer.receive()`:
   a. Відкриває транзакцію БД (`transaction.atomic()`).
   b. Виконує `Lot.objects.select_for_update().get(id=lot_id)` — блокує
      рядок лоту на час транзакції.
   c. Перевіряє: `amount > lot.current_highest_bid` і що аукціон ще не
      завершився (`timezone.now() < lot.ends_at`).
   d. Якщо ставка валідна: створює запис `Bid`, оновлює
      `lot.current_highest_bid` та `lot.current_winner`, зберігає — і лише
      після цього транзакція комітиться, знімаючи блокування рядка.
   e. Якщо ставка невалідна: транзакція відкочується (нічого не пишеться),
      клієнту надсилається помилка `bid_rejected`.
5. Після успішного коміту в БД оновлюється кеш у Redis (`current_highest_bid`
   для швидкого читання новими підключеннями).
6. Consumer публікує подію `bid_accepted` у групу каналу `lot_<lot_id>` через
   channel layer.
7. Channel layer (Redis pub/sub) розсилає подію всім consumer'ам, підписаним
   на цю групу — незалежно від того, на якому ASGI-воркері вони працюють.
8. Кожен consumer пересилає подію своєму WebSocket-клієнту — усі учасники
   аукціону бачать нову найвищу ставку практично одночасно.

## 6. Масштабування та балансування навантаження

- Кілька ASGI-воркерів (Daphne/Uvicorn) можуть працювати паралельно за
  Nginx, оскільки стан WebSocket-груп зберігається не в пам'яті процесу, а
  в Redis (channel layer) — будь-який воркер може обслуговувати будь-якого
  клієнта лоту.
- PostgreSQL залишається єдиним джерелом істини і точкою серіалізації для
  конкурентних ставок (чере `SELECT ... FOR UPDATE`), тому коректність
  гарантується навіть при горизонтальному масштабуванні воркерів.
- Redis-кеш знімає навантаження читання (наприклад, відображення поточної
  ставки при відкритті сторінки лоту) з PostgreSQL.
